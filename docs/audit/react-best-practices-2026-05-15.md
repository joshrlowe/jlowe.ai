# React / Next.js Best-Practices Audit — 2026-05-15

Scope: `pages/**/*.{ts,tsx}`, `components/**/*.{ts,tsx}`, `lib/**/*.{ts,tsx}`. Tests, mocks, fixtures, scripts excluded.

Reference: Vercel React/Next.js best-practices rule set (70 rules, prioritized by impact). Severity prefix uses the Vercel rule namespace: `async-`, `bundle-`, `server-`, `client-`, `rerender-`, `rendering-`, `js-`, `advanced-`. Severity ranks: **CRITICAL > HIGH > MEDIUM > LOW**.

Findings are GitHub-style checkboxes. Each line points at a specific file/line, names the rule, and proposes a one-liner fix.

## 1. Request waterfalls (CRITICAL)

- [ ] **[CRITICAL/async-parallel] components/Chat/ChatMessage.tsx:42-48** — `/api/chat/feedback` POST is fire-and-forget but `await`ed inside the `vote()` handler before the toast lights up. Fine, but the **trace ID isn't even threaded to the feedback request until after the assistant message stream finishes**; consider piping a `traceId` ref so the user can vote mid-stream. Low priority — flagged for completeness.
- [ ] **[CRITICAL/async-parallel] components/Footer.tsx:74-112** — Footer mounts on every page and hits `/api/contact` + `/api/site-settings` from the client on every load, then re-fetches on `focus`. Plus the cache-buster `?_t=Date.now()` defeats the CDN. This is a **5-request, 100% miss-rate per navigation** waterfall: page HTML → hydrate → 2 fetches → re-render. **Fix:** hoist via `getStaticProps` per-page (or fetch once in `_app.tsx` and pass via context); drop the cache-buster — let `revalidate: 60` on `/api/site-settings` handle freshness.
- [ ] **[CRITICAL/async-parallel] components/GitHubContributionGraph.tsx:206-263 + 295-324** — `CalendarWrapper` runs **two parallel-but-redundant fetches**: a debug `testAPI()` to `github-contributions-api.jogruber.de` AND the lazy import of `react-github-calendar` (which calls the same API internally). Both run on mount, doubling network use, and the `testAPI` block contains 6 `console.log` statements shipped to production. **Fix:** delete the entire `testAPI` `useEffect` (lines 206-263) — it's debug code that landed in main.
- [ ] **[CRITICAL/async-parallel] pages/articles/[topic]/[slug].tsx:57-71** — `fetchLikeStatus` fetches like data in a client `useEffect` even though `_count.likes` is **already served via `getStaticProps`** (line 320-329). Two round-trips to render one heart icon. **Fix:** pass `initialLikes` from SSR and drop the client fetch; refresh on user action only.
- [ ] **[HIGH/async-parallel] components/Articles/PostLikeButton.tsx:21-48** — Even when `initialLikes` is supplied from SSR, mount runs a **second** `/api/posts/.../like` GET to check personal liked-state. Combined with the parent's redundant fetch above, the user pays 2 client round-trips before the heart can be tapped. **Fix:** read the localStorage flag synchronously in `useState` initialiser, only call the API if not present.
- [ ] **[HIGH/async-parallel] pages/admin/dashboard.tsx:34-71** — `fetchDashboardData` performs a single `/api/admin/projects` GET, then **does pagination/sorting/slicing client-side** for stats. Even with `requireAuth` returning `{ props: {} }`, this could move to `getServerSideProps` to remove the loading flash entirely.
- [ ] **[HIGH/async-cheap-condition-before-await] pages/api/chat.ts:171-179** — `prisma.chatSession.upsert` always runs even when the session already exists and is unchanged. The `update: {}` is a no-op write that grabs a row lock and bumps `updatedAt`. **Fix:** `findUnique` first; only `create` when null. Saves a write on the hottest path (every chat message).
- [ ] **[HIGH/async-parallel] pages/api/chat.ts:188-205** — The 3-way `Promise.all` (persist user msg / classify intent / search RAG) is great. BUT `searchKnowledge` itself runs **serial** awaits: `generateQueryEmbedding` (1 Bedrock call) **then** the hybrid query, then `rerankCandidates` (1 Cohere call). Embedding gen and the cookie-touching Prisma upsert above could overlap — they're independent. **Fix:** start `generateQueryEmbedding(userText)` immediately after parsing, before the upsert/transaction.
- [ ] **[MEDIUM/async-parallel] components/Articles/PostComments.tsx:266-282** — `fetchComments` and the page's other client fetches all kick off after hydration with no parallelism opportunity. Acceptable, but consider moving comment hydration into `getStaticProps` for the article page.
- [ ] **[MEDIUM/async-defer-await] lib/rag/vector-search.ts:117-126** — `Promise.all([semanticPromise, keywordPromise])` is fine, but the `.then(r => { span.end(); return r; })` wrappers cause each branch to wait on the other before its span closes (only because the outer `await` blocks). Cosmetic — flagged so the observability author knows the spans race.

## 2. Bundle size (CRITICAL)

- [ ] **[CRITICAL/bundle-dynamic-imports] pages/contact.tsx:15** — `react-text-transition` (>50 KB gzipped, includes `react-spring`) is imported statically and runs **only on `/contact` for a 3-word carousel**. Hard requirement to ship. **Fix:** `const TextTransition = dynamic(() => import("react-text-transition"), { ssr: false })`, render plain text on first paint. Or replace with CSS keyframe animation — the word list is 3 strings.
- [ ] **[CRITICAL/bundle-dynamic-imports] components/admin/MarkdownEditor.tsx:2 + pages/articles/[topic]/[slug].tsx:11 + components/ui/MarkdownContent.tsx:1 + components/Project/ProjectDetail.tsx:5** — `react-markdown` + `remark-gfm` (combined ~80 KB gzipped) are imported statically in 4 places. `MarkdownEditor` only renders Markdown when `isPreview === true` — pay-on-toggle. `ProjectDetail`, `ArticleDetailPage`, `MarkdownContent` need it for first paint, but the editor case is wasteful. **Fix:** `const ReactMarkdown = dynamic(() => import("react-markdown"))` inside `MarkdownEditor.tsx` gated on `isPreview`.
- [ ] **[CRITICAL/bundle-dynamic-imports] pages/_app.tsx:11-12** — `gsap` + `gsap/ScrollTrigger` are statically imported at the app shell, so **every page** (including `/contact`, `/articles`, `/admin/*`) pays the GSAP cost (~70 KB) even if it never animates. Pages Router has no equivalent of RSC, so this can't be eliminated, but the `registerPlugin` call at module top-level is what forces the static import. **Fix:** push GSAP registration into a `_app` `useEffect` that dynamically imports `gsap` once per session, or accept this as a sitewide design decision and document it.
- [ ] **[HIGH/bundle-dynamic-imports] components/HeroSection.tsx:47** — `react-typed` is correctly `dynamic({ ssr: false })`. Good. But it's **also imported a second time at line 205** inside the same component for the loop animation — that's only fine because the dynamic factory caches; verify the bundler isn't tree-shaking issues. No fix needed if `next/dynamic` gives a stable handle.
- [ ] **[HIGH/bundle-dynamic-imports] pages/_app.tsx:10 + 9** — `react-toastify` (CSS + JS, ~30 KB) and `@vercel/analytics/react` ship to every visitor including the design sandbox. Toastify is used in `<ChatMessage>` (mounted on every page via `ChatWidget`) — unavoidable. Analytics is also unavoidable for prod tracking. Acceptable, flagged for context.
- [ ] **[HIGH/bundle-dynamic-imports] components/GitHubContributionGraph.tsx:305** — Correctly uses `import("react-github-calendar")` inside an effect. Good. But the **3-tier loading state + 15-second timeout + parallel debug fetch** are ~150 LoC of complexity that wouldn't be needed if the wrapper component was itself the `dynamic()` boundary instead of doing dynamic-import-inside-effect dance.
- [ ] **[HIGH/bundle-barrel-imports] components/ui/index.ts** — Re-exports `Badge`, `Button`, `Card`, `Pagination`, etc. from one file. `import { Button } from "@/components/ui"` pulls the whole barrel even with tree-shaking unless every transitive import is pure ESM. With React Toastify CSS side-effects already in the graph this is usually a non-issue, but verify with `npm run build -- --analyze` (no analyzer script exists — add one).
- [ ] **[HIGH/bundle-conditional] pages/index.tsx:43-53 + 55-59** — `GitHubContributionGraph` and `SpaceBackground` correctly use `dynamic({ ssr: false })`. SpaceBackground is **170 KB+ of Three.js** — fine to dynamic-load since it's below-the-fold for the typing animation, but consider an `IntersectionObserver` hold so the import doesn't begin until the user scrolls (currently it begins immediately on mount).
- [ ] **[MEDIUM/bundle-defer-third-party] pages/_app.tsx:69-72** — Service-worker registration runs on every mount inside a `useEffect`. Fine, but could be wrapped in `requestIdleCallback` so it doesn't compete with hydration.
- [ ] **[MEDIUM/bundle-preload] pages/_app.tsx:79-103** — The "prefetch on hover" handler attaches a `mouseenter` listener to every `<a>` and calls `router.prefetch(href)`. This is exactly the `bundle-preload` recommendation. Good. But it runs on *every* anchor, including external links and footer mailto:. **Fix:** the `href.startsWith("/")` check passes for these but `router.prefetch` will then fail silently — fine. Lower-priority: scope to nav anchors only.
- [ ] **[LOW/bundle-analyzable-paths] components/admin/HomeSettingsSection.tsx:4** — `import { LoadingSpinner, adminStyles } from "./shared"` — relative barrel. Fine for `@next/bundle-analyzer`, but explicit path imports (`./shared/LoadingSpinner`) help tree-shakers and the agent navigability story.

## 3. Server-side performance (HIGH)

- [ ] **[HIGH/server-parallel-fetching] pages/index.tsx:131-159** — `getStaticProps` runs **5 sequential Prisma queries**: `welcome.findFirst` → `project.findMany` → `contact.findFirst` → `post.findMany` → `pageContent.findUnique`. None depend on each other. **Fix:** wrap in a single `Promise.all([...])`. Build time scales linearly; one ISR regen pays the full chain.
- [ ] **[HIGH/server-parallel-fetching] pages/articles/[topic]/[slug].tsx:319-329** — Single `prisma.post.findUnique` with nested `_count.comments` and `_count.likes`. Acceptable but verify Prisma generates a single SQL query (it should via `_count`). The bigger win: `getStaticPaths` (line 292-308) does `findMany` of every published post on every build — for 100 posts this is fine, for 10,000 it'd timeout. Flag and document.
- [ ] **[HIGH/server-hoist-static-io] lib/fonts.ts** — Not opened but referenced by `_app.tsx`. Next.js `next/font` loads at module init by design; verify `lib/fonts.ts` exports stable, hoisted font instances (don't re-initialize inside components). Likely already fine.
- [ ] **[MEDIUM/server-cache-react] pages/about.tsx:244-257** — `Promise.all` over four `findFirst` calls. Good parallelism. Each ISR regen pays one of these every 60s. Consider a single denormalized SQL view in Postgres if this becomes a build-time bottleneck.
- [ ] **[MEDIUM/server-parallel-fetching] pages/articles/index.tsx:225-245** — `recentPosts = await prisma.post.findMany(...)` **then** `allPosts = await prisma.post.findMany(...)`. They're sequential; second only needs `topic` + `tags`. **Fix:** `Promise.all`.
- [ ] **[MEDIUM/server-serialization] pages/projects.tsx:369** — `JSON.parse(JSON.stringify(projects))` to "deserialize" Prisma Date instances. Same in 5+ other `getStaticProps`. Each deep-clones the entire dataset twice. **Fix:** write a typed `serializeForJson(prisma...)` helper that returns ISO strings on Date fields without round-tripping JSON (1 pass instead of 2). Or use `superjson`/`devalue`.
- [ ] **[MEDIUM/server-after-nonblocking] pages/api/chat.ts:308-334** — The final `prisma.$transaction` (create assistant message, updateMany user intents, update session) runs **after** the stream completes but **before** `res.end()`. The client has all the text already; the transaction is non-blocking observability. **Fix:** Pages Router doesn't have `unstable_after()`; the closest equivalent is to call `res.end()` first then `await trans.flush()` — but that risks Vercel function cancellation. Document as known.

## 4. Client-side data fetching & effects (MEDIUM-HIGH)

- [ ] **[HIGH/rerender-derived-state-no-effect] components/HeroSection.tsx:63-79** — `useEffect` sets `mounted = true` and conditionally `animationReady = true` based on `sessionStorage.getItem("introAnimationPlayed")`. **`introAnimationPlayed` is a static-on-read string** — it can be read once in a `useState` initializer (`useState(() => sessionStorage.getItem(...) === "true")`). Saves one render cycle on every home-page mount.
- [ ] **[HIGH/rerender-derived-state-no-effect] components/SpaceBackground/index.tsx:46-69** — Same pattern: `setMounted(true)` then re-reads `sessionStorage` + `matchMedia` inside `useEffect`. The mount flag could be `useSyncExternalStore` or the entire effect could read sync from `window` checks in a `useState` initialiser guarded by `typeof window !== "undefined"`. With the current 4-state flag dance (`mounted`, `reducedMotion`, `animationComplete`, `triggerExplosion`, `skipAnimation` — five `useState`s in one component) this generates several extra renders before Three.js mounts.
- [ ] **[HIGH/client-event-listeners] pages/_app.tsx:99-101** — `document.addEventListener("mouseenter", handleLinkMouseEnter, true)` with capture phase fires on **every element**, not just anchors. On a long article page this fires hundreds of times per second. **Fix:** use a single `mouseover` listener on `document.body` (bubbles, fires once per element), or attach handlers per-anchor via `useEffect` watching the DOM (`MutationObserver`), or drop entirely and rely on `<Link prefetch>`.
- [ ] **[HIGH/client-passive-event-listeners] components/Header.tsx:28-35** — `addEventListener("scroll", handleScroll)` with no `{ passive: true }`. The handler only reads `window.scrollY` (passive-safe). **Fix:** `addEventListener("scroll", handleScroll, { passive: true })` — same as `ScrollProgress.tsx:30` already does.
- [ ] **[HIGH/rerender-derived-state-no-effect] components/Footer.tsx:73-112** — `setMounted(true)` *and* duplicates client-side fetches that should be at the page level (see waterfall finding above). The `isMounted` flag pattern was correct in React 17; in React 18 with StrictMode the cleanup races. **Fix:** use `AbortController` to cancel the fetch on unmount; drop `isMounted`.
- [ ] **[MEDIUM/rerender-defer-reads] components/Chat/ChatPanel.tsx:30-32** — `useState` for `messages`, `input`, `loading` — fine. But `setMessages([...prev])` is called inside a `while` loop on every SSE chunk (line 100-110), forcing a render per delta. With a 500-token assistant response that's 500+ renders. **Fix:** debounce/batch updates via `requestAnimationFrame` or `useTransition`/`startTransition`, since the streaming text is non-urgent visually. Worth a microbench before committing.
- [ ] **[MEDIUM/client-localstorage-schema] components/Articles/PostLikeButton.tsx:22, 34-37, 71-73** — `localStorage.getItem("likedPosts")` is parsed as `string[]` with no version, no schema check, no size cap. If the JSON is corrupt it throws synchronously and crashes the component. **Fix:** wrap `JSON.parse` in try/catch, default to `[]`, version the key (`likedPosts:v1`).
- [ ] **[MEDIUM/rerender-functional-setstate] components/Chat/ChatPanel.tsx:100-110** — `setMessages((prev) => { const next = [...prev]; next[next.length - 1] = ...; return next; })` — correct functional update. Good. But the spread-and-mutate pattern is O(N) per chunk; for a 500-message session it's quadratic. Not a real issue yet, flagged.
- [ ] **[MEDIUM/rerender-derived-state-no-effect] components/Articles/PostComments.tsx:280-282** — `useEffect(() => { fetchComments(); }, [fetchComments])` — fine; `fetchComments` is wrapped in `useCallback`. But the call has no SSR fallback; user sees a `[...Array(3)]` skeleton for every article view even when there are 0 comments. **Fix:** include initial comments in `getStaticProps` of the article page; only refetch on user action.

## 5. Re-render & memoization (MEDIUM)

- [ ] **[MEDIUM/rerender-no-inline-components] pages/articles/[topic]/[slug].tsx:191-269** — The `components={{...}}` object passed to `<ReactMarkdown>` defines **15 inline JSX components per render**. Every article view triggers ReactMarkdown to re-mount all these. **Fix:** hoist the components map to module scope (`const markdownComponents = { code: ..., h1: ..., ... }`).
- [ ] **[MEDIUM/rerender-memo-with-default-value] components/HeroSection.tsx:125-155** — `typingStrings`, `primaryCta`, `secondaryCta`, `techBadges` default objects are constructed inline on every render with `??`. **Fix:** module-level `const DEFAULT_TYPING_STRINGS = [...]`, same for badges. Saves stable identity to children.
- [ ] **[MEDIUM/rerender-lazy-state-init] components/SpaceBackground/index.tsx:28-32** — Multiple `useState(false)` could collapse to one `useReducer` since they all flip in lockstep on intro complete. Minor.
- [ ] **[MEDIUM/rerender-simple-expression-in-memo] pages/articles/[topic]/[slug].tsx:74-77** — `useMemo(() => post ? \`...${post.topic}/${post.slug}\` : "")` is wrapped in `useMemo` for a 2-line string concat. The cost of `useMemo` exceeds the cost of the string template. **Fix:** drop the `useMemo`, just compute inline.
- [ ] **[MEDIUM/rerender-derived-state-no-effect] components/Articles/PostComments.tsx:25-32** — `CommentItem` initialises `likes`, `dislikes`, `userVote` from props in `useState` — fine for first mount, but if the parent re-renders and passes new prop values, child state goes stale. **Fix:** derive `likes` from a `useRef`-cached version-tracked prop, or treat the component as fully controlled.
- [ ] **[MEDIUM/rerender-derived-state-no-effect] components/Articles/PostLikeButton.tsx:17, 21-48** — `useState(initialLikes)` then `useEffect` does another fetch and overwrites it. State derived from props that gets overwritten by side-effect = recipe for race conditions. See waterfall finding above for the structural fix.
- [ ] **[MEDIUM/rerender-split-combined-hooks] pages/projects.tsx:69-99** — `useMemo` recomputes `availableTags` and `availableStatuses` together. They both depend on `projects` only, so OK. But the inner JSON parsing per-project per-render is O(N×P) where P is projects. **Fix:** pre-normalise tags/statuses in `getStaticProps` and pass as separate arrays.
- [ ] **[LOW/rerender-memo] components/Chat/ChatMessage.tsx:33** — `ChatMessageBubble` re-renders on every parent state change even if its `message` prop didn't change. Worth a `memo()` wrapper since the chat panel re-renders per SSE chunk and there can be 10+ message bubbles.

## 6. Rendering performance (MEDIUM)

- [ ] **[MEDIUM/rendering-svg-precision] components/RecentActivity.tsx:41-84, components/Header.tsx, components/Footer.tsx, etc.** — Inline SVGs sprinkled throughout (50+ across the codebase). Each is small individually but they're all shipped in every JS bundle since they're JSX, not imported assets. **Fix:** extract to a single `<Icon name="..." />` sprite map or `next/image` static SVG imports.
- [ ] **[MEDIUM/rendering-conditional-render] pages/about.tsx:161-226** — Heavy use of `&&` for conditional rendering, e.g. `serializedData?.technicalSkills && Array.isArray(...) && length > 0 && (<section>...)`. Falsy values like `0` would render the literal `0`. Use ternary or extract to a `<MaybeSection>` helper.
- [ ] **[MEDIUM/rendering-hoist-jsx] components/Footer.tsx:28-62** — `socialIcons` Record is module-level. Good. But the `<svg>` JSX inside is re-evaluated on every Footer render because JSX is not memoized. Hoist each icon to a stable React.memo'd component.
- [ ] **[LOW/rendering-content-visibility] pages/articles/index.tsx:144-198** — Paginated post list with full markdown excerpts. For long pages, `content-visibility: auto` on each article card improves rendering perf. Acceptable to skip.
- [ ] **[LOW/rendering-script-defer-async] pages/_app.tsx:69-72** — Service worker registration runs synchronously inside `useEffect`. Wrap in `requestIdleCallback` (with fallback to `setTimeout(..., 1)`) to avoid competing with hydration.

## 8. React 19 / Next.js 16 migration blockers (Tier 3 ADR input)

- [ ] **[CRITICAL/migration] Repo-wide** — **17+ files start with `/* eslint-disable react-hooks/set-state-in-effect, react-hooks/preserve-manual-memoization, react-hooks/immutability, react-hooks/exhaustive-deps ... */`**. Examples: `pages/_app.tsx:1-2`, `pages/index.tsx:1`, `pages/projects.tsx:1`, `pages/contact.tsx:1`, `pages/about.tsx:1`, `components/HeroSection.tsx:1-3`, `components/FeaturedProjects.tsx:1-2`, `components/RecentActivity.tsx:1-2`, `components/GitHubContributionGraph.tsx:1-3`, `components/Footer.tsx:1-3`, all admin pages, all article pages. These disables hide patterns that **the React 19 compiler will actively complain about** (setState-in-effect, dep-array violations). **Fix:** systematic effect refactor; this is a tier-3 ADR worth.
- [ ] **[HIGH/migration] components/ui/Button.tsx, Card.tsx, Pagination.tsx, Badge.tsx** — Heavy `forwardRef` boilerplate (~10 LoC of wrapper per component). React 19 makes `ref` a regular prop on function components — these can drop the `forwardRef` wrappers entirely after upgrade. Document in upgrade ADR.
- [ ] **[HIGH/migration] components/HeroSection.tsx:47-50** — `dynamic(() => import("react-typed").then((mod) => mod.ReactTyped))` — verify `react-typed` v2 is React 19 compatible (its peerDeps list React 18 only as of this audit). Flag for `package.json` audit during upgrade.
- [ ] **[HIGH/migration] components/GitHubContributionGraph.tsx:312** — Manual check `Component.$$typeof` to detect forwardRef-flavoured imports. React 19 removes `$$typeof` symbols for some forwardRef paths. **Fix:** rely on `typeof Component === "function"` only after the wrapper is dropped.
- [ ] **[MEDIUM/migration] All `getServerSideProps` files** — Next 16 deprecation track: Pages Router stays supported, but the `requireAuth` middleware pattern (`lib/auth.ts:requireAuth`) returns `{ props: {} }` and relies on Next.js Edge middleware for the actual gate. The middleware contract was hardened in Next 15.4+ — verify `middleware.ts` matchers still apply correctly. Flag.
- [ ] **[MEDIUM/migration] pages/articles/[topic]/[slug].tsx:191-269** — `components={...}` prop to `ReactMarkdown` uses `as any` casts to satisfy types. `react-markdown` v10 (React 19 compatible) tightens these types. Refactor to typed components before upgrading.
- [ ] **[LOW/migration] pages/_app.tsx:30-32** — `gsap.registerPlugin(ScrollTrigger)` at module init. React 19 strict-mode StrictEffects double-render won't break this (it's a no-op on second call), but flag for verification.
- [ ] **[LOW/migration] All `/* eslint-disable @typescript-eslint/no-explicit-any */`** — Repo-wide. React 19 + TS 5.6+ has better inference; many `any` casts can become typed. Tier-3 cleanup.
