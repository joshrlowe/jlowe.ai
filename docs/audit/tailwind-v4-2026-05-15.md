## Findings

### `[low] styles/toast.css:6` — references undefined CSS variable `--color-bg-dark-alt`

`toast.css` line 6 sets `background-color: var(--color-bg-dark-alt);` but `--color-bg-dark-alt` is **not defined** anywhere in `globals.css` (nor elsewhere in the repo). Toast notifications will fall back to transparent / inherited background, which on the dark space-themed body will likely still be black-ish but is not the intended look.

**Fix (recommendation only — out of audit scope to apply):** either
- (a) rename to an existing token, e.g. `var(--color-bg-card-solid)` (`#0c0c0c`) or `var(--color-surface-elevated)` (`#121212`), or
- (b) add `--color-bg-dark-alt` to the `@theme` block in `globals.css` if a distinct admin-toast background is intended.

Severity is `low` because the dark global body background masks the missing value visually.

## Per-check results (no findings)

### 1. `@theme` block correctness — PASS

- One block, root-level, lines 10-146. Properly formed CSS custom properties throughout.
- No nested `@theme`, no `@theme inline` (correct — `@theme inline` is a shadcn-specific pattern for mapping a separate `:root`/`.dark` variable layer, which this project doesn't have).
- No v3-isms: no `@tailwind base/components/utilities` directives, no `module.exports` config, no `plugins: [...]` block, no `@plugin` directives (none needed).
- Token naming follows v4 convention: `--color-*` generates `bg-*` / `text-*` / `border-*` utilities; `--space-*`, `--radius-*`, `--shadow-*`, `--font-family-*`, `--text-*`, `--container-*`, `--transition-*` are all in valid v4 token namespaces.
- No orphans: every token defined in `@theme` is either used downstream in the file or is part of the documented design system (Supernova or Liquid Heat).

### 2. OKLCH usage — N/A (acceptable)

The project is hex + rgba throughout. OKLCH is the v4 default for the built-in palette but is **not required** for custom tokens. For a personal site with a designer-curated palette (Supernova / Liquid Heat), hex is fine and was a deliberate choice — the heat-temperature semantics in `--color-heat-peak` etc. (lines 127-134) describe perceptual intent better in plain hex than they would in OKLCH coordinates. **No action.**

### 3. Custom utilities / `@layer` — PASS

- **No `@layer` directives at all.** Custom utilities (`.font-heading`, `.glass`, `.btn-primary`, `.gradient-text-fire`, `.animate-ember`, the Liquid-Heat suite, etc.) are declared as plain class rules outside any layer.
- For a project that does not use `@apply` and does not need to interleave with Tailwind's generated layers, this is **acceptable and idiomatic in v4**. There is no `@layer components { ... }` ceremony to add — these classes already win against Tailwind utilities by source order (`@import "tailwindcss"` is at the top of the file, custom classes come after) and by specificity equivalence.
- If a future need arises to have a utility class be overridable by inline Tailwind utilities, that single class could be wrapped in `@layer components { ... }`, but right now no such need exists.

### 4. `@apply` usage — PASS

Zero `@apply` directives in `globals.css` or anywhere in the codebase (verified across `styles/`, `components/`, `pages/`). The file uses raw CSS with custom-property references throughout, which is the recommended v4 pattern and avoids the v3 `@apply` performance/cascade pitfalls.

### 5. Section-scoped overrides (line 713+) — PASS, well-expressed

The Liquid-Heat block (lines 678-930) uses the **CSS-variable rebind pattern** for palette swaps:

```css
.cooling-zone {
  --color-primary: var(--color-heat-mid);
  --color-primary-dark: var(--color-ember-decay);
  --color-primary-glow: rgba(196, 32, 16, 0);
  --color-border: rgba(196, 32, 16, 0.18);
  --color-border-glow: rgba(196, 32, 16, 0.28);
}
```

Everything that paints with `--color-primary` (links, borders, hovers, the `.btn-*` family, the `.card`, the `.badge`) inside a `.cooling-zone` subtree automatically picks up the cooled values. This is **strictly better than `dark:` variants** for this use case because:

- It is one rule per zone instead of `dark:` on every utility.
- It composes with the additive Liquid-Heat tokens (`--color-heat-mid`, `--color-ember-decay`) defined in the same `@theme` block (lines 127-134).
- It cleanly expresses the "as the page cools, saturation drops" intent documented in the comment.

The dual Supernova / Liquid-Heat system is well-expressed. No restructuring needed.

Minor observation (not a finding): `.cooling-zone-deep` (line 720) hardcodes `#3a0306` inline rather than promoting it to a token. This is fine if the value is genuinely one-off, which it appears to be.

### 6. Media queries — PASS

Two `@media (min-width: ...)` queries on `.container` (lines 246 and 253) at `640px` and `1024px`. These match Tailwind's `sm` and `lg` breakpoints exactly, so they will **not** conflict with v4's built-in breakpoint utilities — they reinforce them on the same boundary. Two `@media (prefers-reduced-motion: reduce)` queries (lines 608 and 911) handle motion accessibility (see #8). No conflicts.

### 7. PostCSS config — PASS

Correct v4 plugin reference. `@tailwindcss/postcss@^4.1.18` and `tailwindcss@^4.1.18` are pinned in `package.json` devDependencies. `autoprefixer@^10.4.23` is also present (devDependency) but **not** wired into `postcss.config.mjs` — that's fine, Tailwind v4 includes vendor-prefixing internally via Lightning CSS, so the standalone `autoprefixer` entry is dead weight but causes no harm. (Could be removed in a future deps-cleanup pass; not flagging because it doesn't affect Tailwind v4 correctness.)

### 8. Animations — PASS

- Seven `@keyframes` declarations: `float`, `pulse-glow`, `shimmer`, `flicker`, `ember-pulse`, `gradient-shift` (Supernova, lines 517-584) and `liquid-heat-ignite`, `liquid-heat-ignite-inflection`, `liquid-heat-ingot` (Liquid Heat, lines 731-808). All are syntactically correct and namespaced clearly by section.
- Corresponding `.animate-*` and `.ignite-char` / `.ingot-pulse-on-hover` / `.ember-fill-cta` utility classes are well-named and scoped.
