# jlowe-dependency-strategy

A tiered, risk-ordered playbook for upgrading npm dependencies in the jlowe.ai project. The tiers below were verified during the `cleanup/2026-05-15` cleanup branch and **supersede the original dependency playbook** where they conflict. Follow tiers in order; do not skip ahead without explicit user approval.

## Pre-flight (always run first)

1. Confirm working directory is `/Users/jlowe/Projects/jlowe.ai`. If not, abort.
2. Establish a baseline: if no `.audit-baseline-*/` directory exists, snapshot `npm outdated --json` and `npm audit --json` into a fresh `.audit-baseline-<date>/` (e.g. `.audit-baseline-2026-08-11/`) before touching anything — every tier compares its post-bump state against this baseline.
3. Confirm the working tree is clean (`git status --porcelain` returns empty). Stash or commit local changes first.
4. Capture the current state of locks:
   - `npm outdated --json > /tmp/outdated.before.json`
   - `npm audit --json > /tmp/audit.before.json || true`
5. Confirm with the user which tier(s) to run. Default to Tier 1 only unless told otherwise.

## Per-package execution loop

Apply this loop **for every package** in the chosen tier. Never batch multiple package bumps into one commit.

1. `npm install <pkg>@<latest>` (use `--save-exact` only if the package's existing entry in `package.json` is pinned without a range — match the existing style).
2. Run the verification stack in this exact order:
   - `npm test`
   - `npx tsc --noEmit`
   - `npm run lint`
3. If all three pass, commit per package with the message:
   - `chore(deps): bump <pkg> from <old> to <new>`
   - Body should reference the changelog URL and call out any notable behavioral changes you observed.
4. Diff the package's audit/outdated delta against the pre-flight baseline directory to confirm the bump removed the entry (and did not regress another).
5. On test failure (or any verification step failing): **abort the tier immediately**, investigate the failure, then either fix-forward in the same commit or pin-and-defer (revert the bump, document why under `docs/decisions/` or in the user-facing report).

## TIER 1 — Low risk, do first (6 packages)

Sweep + safe majors. Run these in the listed order. Commit each separately.

1. **`npm update`** — patch + minor sweep across all locked packages. One commit, message: `chore(deps): npm update sweep (patch+minor)`. Treat as a single "package" for purposes of the loop above (lint/test/tsc gate). If this fails, bisect by reverting `package-lock.json` chunk-by-chunk before proceeding to majors.
2. **`bcryptjs` 2 → 3** — first run `grep -r bcryptjs lib/ pages/` to determine whether this is runtime (auth) or scripts-only. If it is referenced in `lib/auth.ts` or NextAuth credential paths, smoke test the login flow (`/admin/login`) against a dev server before committing. Hashes generated by v2 remain verifiable in v3.
3. **`dotenv` 16 → 17** — scripts-only impact (no Next.js runtime usage). Smoke test by running `npm run seed:admin` against a throwaway DB. Watch for the v17 quiet-mode default change in CLI output.
4. **`@testing-library/react` 14 → 16** — touches ~172 test files. After bump, the full `npm test` is mandatory (not just affected suites). If breakage is widespread (>10 failing suites), **pin at 15.x interim** (`npm install -E @testing-library/react@15`) and document under `docs/decisions/` for follow-up. v16's removal of legacy fake-timer semantics is the most common breakage source — check `jest.setup.js` for any `jest.useFakeTimers({ legacyFakeTimers: true })`.
5. **`react-markdown` 9 → 10** — 4 call sites only. Module is **already mocked in `jest.config.js`**, so test failures here are almost certainly a real runtime regression. After bump, manually render a comment + an article body in dev to spot-check.
6. **`three` 0.x patch bumps** — version is `0.x` so all bumps are technically "minor" in semver terms but treat each as its own commit. Background scene + WebGL shaders are load-bearing; after each bump, manually load `/` in dev and confirm `SpaceBackground` + `FluidHeatShader` initialize.

## TIER 2 — Medium risk (3 packages)

Run only after Tier 1 is complete and merged. Get user confirmation before starting.

1. **`@vercel/analytics` 1 → 2** — wrapper at `lib/analytics.ts`, mounted in `pages/_app.tsx`. v2 reorganized the React entrypoint (`@vercel/analytics/react` → `@vercel/analytics/next` or similar). After bump, verify the import path in `_app.tsx` still resolves and that the analytics beacon fires in dev (network tab → look for `/_vercel/insights/view`).
2. **`react-toastify` 10 → 11** — `components/ToastProvider.tsx` plus ~7 emit sites. v11 changed the CSS import path (`react-toastify/dist/ReactToastify.css` → `react-toastify/ReactToastify.css` or `/dist/ReactToastify.min.css` depending on bundler). **Specifically verify the CSS import path** — a wrong path produces unstyled toasts at runtime with no build error. Manually trigger a toast in dev (e.g., from an admin save action) and confirm it renders styled.
3. **`jest` 29 → 30 + `jest-environment-jsdom` 29 → 30** — must be bumped **as a pair, in a single commit** (jest core and jsdom env are version-locked). After bump, verify:
   - `next/jest` wrapper is still compatible (check `jest.config.js` — if it imports from `next/jest` it should work, but watch for ESM/CJS resolution warnings).
   - `testEnvironmentOptions: { customExportConditions: [""] }` is still present and effective for MSW 2.x interop. If MSW handlers break, re-add or relocate this option.
   - The `moduleNameMapper` workaround stripping `.js` extensions still functions.

## TIER 3 — Deferred past 2026-05-31 (per ADR)

**Do NOT run these as part of a routine upgrade pass.** They are documented here so future sessions know they are intentionally held back, not forgotten. Each is gated on its own ADR review.

- `react` 18 → 19, `react-dom` 18 → 19 — coordinated React 19 migration; requires re-validating Three.js fiber, GSAP, and SSR streaming behavior.
- `next` 15 → 16 — Pages Router compat must be re-verified; middleware/edge runtime changes likely.
- `prisma` 5 → 7, `@prisma/client` 5 → 7 — see the `prisma-upgrade-v7` skill. Hard-blocked on the raw-SQL pgvector/tsvector code in `lib/rag/` and the driver-adapters requirement.
- `@react-three/drei` 9 → 10, `@react-three/fiber` 8 → 9 — coupled to the React 19 bump.
- `eslint` 9 → 10, `@eslint/js` 9 → 10 — flat-config breaking changes; lint rules in `eslint.config.mjs` need a full re-audit.
- `undici` 7 → 8 — transitive in most cases; only direct-bump if a security advisory forces it.
- `typescript` 5 → 6 — risk of cascading type errors across the freshly TS-migrated codebase (commit `357d857`).
- `marked` 15 → 16+ — **pinned at v15 per `docs/decisions/0003-pin-marked-v15.md`**: v16+ is ESM-only and jest 29 cannot transform it, so the unpin is gated on the jest 30 upgrade. Only import is `marked.lexer()` in `lib/rag/chunker.ts:9` (RAG ingestion, not rendering); when the pin is lifted, verify chunker output via `npm run build:embeddings:legacy` on a small slice.

If a user explicitly asks for one of these, **do not silently start the loop** — first surface the ADR/deferral, confirm the user wants to override the deferral, and treat the upgrade as a multi-commit migration project (not a routine bump).

## STRIKE list — remove from any future upgrade tracker

- **`react-intersection-observer`** — listed as outdated in `.audit-post-phase1/outdated.json` (9.16.0 → 10.0.3) but **not imported anywhere in the codebase** as of 2026-05-15. If you encounter it in `npm outdated`, the correct action is `npm uninstall react-intersection-observer`, not a version bump.

When generating new upgrade reports, omit struck packages from the table entirely, and note their strike status in the report appendix.

## NEVER auto-upgrade rules (hard stops)

- **Never bump a package whose changelog mentions BREAKING** (any case) without explicit human review and acknowledgment. Pause the loop, print the relevant changelog excerpt, and wait.
- **Never bump a package that fails the test suite.** No "the test is flaky, I'll commit anyway." Either fix the test in the same commit or revert the bump.
- **Never bypass `--ignore-scripts`.** The `postinstall` hook runs `prisma generate`, which is required for builds and for the Prisma Client API to match the schema. Running `npm install --ignore-scripts` leaves the generated client out of sync and silently breaks downstream tooling.
- **Never combine multiple package bumps into one commit** (except the explicitly-paired jest + jest-environment-jsdom pair in Tier 2). Per-package commits are required so a regression can be reverted surgically.
- **Never bump a Tier 3 package as part of a routine pass** — Tier 3 requires its own session, its own ADR review, and explicit user override.

## Final report (after each session)

After completing one or more tiers, produce a short report:

1. Packages bumped this session, with old → new versions and commit SHAs.
2. Packages attempted but reverted, with the reason.
3. Audit/outdated delta vs the pre-flight baseline directory (count of resolved findings, any new findings).
4. Tier(s) remaining and recommended next session timing.
5. Any package the user should consider re-tiering (e.g., a Tier 2 package whose ecosystem has stabilized enough to move to Tier 1 next pass).
